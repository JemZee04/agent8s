# agent8s — инструкция на русском

Telegram-бот, который управляет headless-агентами (Claude Code, Codex — и
любыми другими, см. раздел «Добавить ещё одного агента») поверх локальных
git-репозиториев. Каждая задача выполняется в отдельном `git worktree`,
состояние хранится в SQLite и в самом git, а не в контексте модели — если
агент внутри задачи что-то «забудет», внешний автомат всё равно знает, на
каком шаге он находится.

```
Telegram ── бот на aiogram ── SQLite (проекты, задачи, session_id) ── git worktree ── claude -p / codex exec
```

(Полное техническое описание — в [README.md](README.md) на английском. Здесь
— практическая инструкция, что и в каком порядке делать.)

## 1. Что нужно перед стартом

- macOS/Linux-машина, на которой будет жить бот (по умолчанию — вручную,
  через терминал; не веб-сервис, входящих портов не открывает).
- Установленные и авторизованные CLI `claude` и/или `codex` — бот сам
  ничего не логинит, просто вызывает то, что уже настроено в системе.
- [uv](https://docs.astral.sh/uv/) для управления зависимостями:

  ```bash
  curl -LsSf https://astral.sh/uv/install.sh | sh
  ```

## 2. Установка

```bash
cp .env.example .env
uv sync
```

Открой `.env` и заполни как минимум два обязательных поля:

- `TELEGRAM_BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather)
  (команда `/newbot`).
- `ALLOWED_CHAT_IDS` — твой числовой Telegram ID (через запятую, если людей
  несколько). Узнать свой ID можно у [@userinfobot](https://t.me/userinfobot).
  Это жёсткий белый список: бот проверяет его раньше любой команды и
  отказывается стартовать, если список пуст.

`.env` никогда не попадает в git (см. `.gitignore`) — там же хранятся все
остальные секреты (Jira/Confluence, Яндекс.Календарь), если ты их подключишь.
Всё остальное в `.env.example` уже имеет рабочие значения по умолчанию.

## 3. Запуск

```bash
./scripts/run.sh
```

Работает в терминале (long polling), без входящих подключений. Останавливается
по Ctrl-C.

При каждом старте бот сам регистрирует список команд в Telegram
(`bot.set_my_commands`) — они появляются с описаниями в меню «/» рядом с
полем ввода, ничего дополнительно нажимать не нужно.

## 4. Работа с проектами

Зарегистрировать существующий репозиторий:

```
/add_project quick-hop /Users/you/Documents/quick-hop
```

Или создать новый с нуля — бот сам сделает папку, `git init`, `README.md` и
`CLAUDE.md` (с заполненными именем/описанием, стек и команды агент допишет
сам по мере работы):

```
/new invoice-svc сервис генерации PDF-счетов
```

Дальше:

```
/projects           — список зарегистрированных проектов
/use quick-hop       — выбрать активный проект для этого чата
/agent claude        — выбрать агента (claude или codex)
/agents              — список доступных агентов
```

## 5. Постановка задач

Просто напиши текстом, что нужно сделать — если в чате нет активной задачи,
бот создаст новую ветку `agent8s/task-<id>` и worktree, запустит выбранного
агента в headless-режиме и пришлёт `git diff --stat` (не пересказ агента —
именно то, что реально изменилось в файлах).

Пока агент работает, бот вживую редактирует одно и то же сообщение с каждым
его шагом: `🔧 Bash: npm test`, `📝 add src/foo.py`, `💬 <короткая мысль вслух>`
— вместо того чтобы молчать до самого конца. Редактирование троттлится
(примерно раз в 2 сек, чтобы не упереться в лимиты Telegram на правку
сообщений), но ни один шаг не теряется — просто попадает в следующую правку.
По завершении то же сообщение заменяется финальным summary агента и
`git diff --stat`.

Если задача уже активна — следующее сообщение будет воспринято как
уточнение и продолжит ту же сессию агента (`--resume`), с тем же живым
прогрессом, а не начнёт всё заново. Это чинит основную проблему
headless-агентов — «он всё забыл».

И claude, и codex по умолчанию отвечают на русском, даже если сама задача
или промпт — на английском (без этого модель заметно тянется к английскому
на кодовых задачах). За это отвечает `RESPONSE_LANGUAGE_INSTRUCTION` в
`src/agent8s/agents/base.py` — проверил вживую на обоих агентах. На сам код
(имена, комментарии) это не влияет — там сохраняется стиль конкретного
репозитория.

```
/diff       — полный diff активной задачи, отдельным файлом
/approve    — закоммитить изменения и смержить ветку в основную (--no-ff),
              удалить worktree. Пушa никуда не делает — только локальный merge.
/drop       — отменить задачу: удалить worktree и ветку, изменения теряются
/status     — какой проект, какой агент, какая задача активна сейчас
```

## 5а. Права на запись вне worktree: /grant

codex реально песочнит запись за пределами своего worktree
(`AGENT8S_CODEX_SANDBOX`, по умолчанию `workspace-write`) — проверил вживую:
задача, которую попросили писать вне worktree, получила настоящий отказ
`operation not permitted` от песочницы, а не выдумку агента. У claude
такого ограничения нет (его Bash/Edit/Write идут куда угодно, куда достаёт
пользователь ОС — см. раздел «Безопасность» ниже), так что это касается
только codex.

```
/grant /Users/you/go/src/other-service
```

У `codex exec resume` нет `--add-dir` (проверил напрямую по `--help` — флаг
есть только у самого `exec`, не у `resume`), но песочницу всё же можно
расширить на каждом вызове через `-c
sandbox_workspace_write.writable_roots=[...]` — проверил вживую, что это
именно *добавляет* папку к правам по умолчанию (cwd остаётся доступен на
запись), а не заменяет их. `/grant` запоминает папку за задачей, и она
применяется уже со следующего сообщения — неважно, продолжает оно текущую
сессию или начинает новую: сессия и память диалога не теряются. Проверил
вживую: без гранта — отказ, сразу после гранта та же самая запись проходит.
Для claude `/grant` тоже запоминает папку (передаётся как `--add-dir` в
следующий вызов), но прямо говорит, что расширять там нечего — ограничения
не было изначально.

**Не выполняй** собственные советы агента вроде «запусти `codex resume` в
терминале» при отказе в доступе — это обходит трекинг agent8s целиком, и
понимание бота о сессии/diff задачи разъедется с тем, что реально произошло
на диске.

## 5г. Десктоп-приложение

Нативное окно с полноценными чатами (как в десктопных Codex и Claude) поверх той же оркестрации:
несколько чатов работают параллельно, каждый в своём worktree, а **агента и модель можно менять
прямо внутри одного чата без потери контекста**.

```bash
uv sync --extra desktop                      # pywebview (нативное окно WKWebView, без Electron)
(cd desktop-ui && npm install && npm run build)
uv run agent8s-desktop                       # --no-window — только адрес, чтобы открыть в браузере
```

Telegram-токены не нужны; база и список проектов общие с ботом.

- **Смена агента.** У claude и codex несовместимые форматы нативных сессий, поэтому каноническую
  историю хранит приложение. Когда агент берёт чат (или начинает его) и пропустил ходы, к его
  следующему запросу добавляется компактная выжимка именно этих ходов и состояние рабочей папки.
  Смена только модели (тот же агент) просто продолжает нативную сессию. Вывод инструментов в
  выжимку намеренно не попадает: источник правды — файлы на диске.
- **Где мой код?** В шапке всегда видны проект, ветка и путь к worktree (клик — скопировать,
  «Открыть папку» — Finder; Терминал и VS Code — в меню ⋯). Режим «Прямо в проекте» работает в самой
  папке проекта, без worktree.
- **Панель изменений** (⇧⌘D): живой дифф, коммит и «влить в <основную ветку>» (при конфликте откат чистый).
- **Живой прогресс:** токены по мере генерации, каждый вызов инструмента, время, «Стоп» (⌘.) убивает
  всю группу процессов агента.
- Клавиши: ⌘N новый чат, ⌘1…9 переход к чату, ⇧⌘D изменения, ⌘. стоп.
- Безопасность: сервер слушает только 127.0.0.1 и требует токен текущего запуска (лежит во
  фрагменте URL, на диск не пишется) плюс проверку Host/Origin — страницы в вашем браузере не могут
  управлять агентами. Ответы агента рендерятся через экранирующий Markdown под строгим CSP.
- Разработка интерфейса: `agent8s-desktop --no-window --port 8765 --token dev` и `npm run dev` в `desktop-ui`.
- Тесты: `uv run pytest`.

Пока нет: импорта сессий Codex (сессии Claude Code импортируются, см. ниже), выжимки истории силами LLM
(транскрипт обрезается, а не пересказывается), очереди сообщений, пока агент занят.

### Установить как приложение

```bash
uv run agent8s-desktop --install-app      # --uninstall-app удаляет его
```

Собирает `~/Applications/agent8s.app` (иконка со скруглёнными углами, своё имя в Dock и строке меню) и настраивает
фоновый сервис из раздела ниже. Дальше: открывайте **agent8s** из Launchpad или Spotlight или закрепите в Dock,
терминал не нужен. Приложение — просто окно на сервисе: если его закрыть, сервис (и связь с телефоном) продолжают
работать, а при открытии оно само запускает сервис, если тот был остановлен. Повторный запуск не открывает второе
окно. Если запуск не удался, диалог объяснит причину (подробности в `~/Library/Application Support/agent8s/logs/`).
После обновления кода выполните `--install-app` ещё раз: приложение и сервис обновятся вместе.

### Фоновый запуск (автозапуск)

```bash
uv run agent8s-desktop --install-service     # --uninstall-service, --service-status
```

Ставит LaunchAgent macOS: безоконный `agent8s-desktop` стартует при входе в систему, перезапускается после
сбоя и держит связь с телефоном независимо от того, открыто ли окно. `agent8s-desktop` без флагов потом просто
открывает окно на этом работающем сервисе. Что важно знать:

- Сервис живёт **вне репозитория**: своя копия кода в отдельном virtualenv, своя база и worktree в
  `~/Library/Application Support/agent8s`. (Процесс, запущенный launchd, не может читать `~/Documents` без
  запроса разрешения, на который некому ответить, и зависает на чтении собственного venv; так этого избегаем.
  При первой установке существующие проекты и чаты копируются в базу сервиса, дальше у него своя.)
- После изменения кода повторите `--install-service`, чтобы обновить копию (безопасно при работающем сервисе).
- Нужные настройки из `.env` (`AGENT8S_RELAY_URL`, `AGENT8S_PREVIEW_ORIGIN`, `AGENT8S_PROJECTS_DIR`,
  `AGENT8S_CLAUDE_*`, `AGENT8S_CODEX_SANDBOX`) копируются в сервис при установке; `.env` репозитория он читать
  не может (там секреты, которые ему не нужны, например токен Telegram).
- Для разработки: `agent8s-desktop --standalone` поднимает свой сервер на данных репозитория.

### Импорт чатов из Claude Code

Боковая панель → «⇩ Импорт» показывает сессии из `~/.claude/projects`; выберите нужные (или «Выбрать все новые»),
и они станут чатами с полной историей. Чат работает на месте, в папке, где шла сессия (`claude --resume`
находит сессию только оттуда), следующий ход Claude продолжает именно эту сессию, а при переключении на Codex ему
передаётся история, как в любом чате. Папки без git импортируются (просто без диффа и коммитов); серые строки —
сессии, чья папка уже удалена или которые запускались из временных папок. Файлы сессий только читаются.
Длинная история подгружается порциями («Показать более ранние сообщения»).

### Читать HTML-файл на телефоне

Тот же диалог **🌐 Превью** показывает HTML-файлы из папки чата (сначала самые свежие — то, что агент только что
сгенерировал) и принимает путь к любому другому `.html`. Mac отдаёт файл вместе с тем, что нужно веб-странице рядом с
ним (картинки, стили, скрипты, шрифты, `.json`/`.txt`/`.md`/`.pdf`), поэтому страница выглядит как надо, а ссылки между
страницами работают. Папка целиком **не** раздаётся: скрытые файлы, `..`, симлинки наружу и всё прочее (ключи, `.env`,
базы) отвечают 404. Страницы, написанные под дерево папок, тоже работают: приложение читает HTML и, если он ссылается на
`../assets/style.css` или на корень сайта (`/assets/app.css`), раздаёт нужную папку выше — но не дальше проекта, которому
принадлежит файл, и вообще не расширяет раздачу для файла вне всех проектов — и открывает страницу по адресу, которого
ждут её ссылки (в диалоге видно, какая папка раздаётся). Адреса папок, `/docs/intro` → `intro.html` и `intro/index.html`
работают как на обычном хостинге, а всё, что страница запросила и не получила, перечислено в диалоге. Срок жизни ссылки, доверие к реле и второе имя сервера — как у превью сайтов ниже.

### Открыть на телефоне сайт, который агент запустил на `localhost`

Попросите агента «запусти сайт на localhost» и откройте **🌐 Превью** в чате (на десктопе или телефоне): там список
того, что слушает порты на этом Mac (сначала процессы из папки чата, затем похожие на dev-сервер, остальное
свёрнуто), либо можно ввести порт. Ссылка живёт 8 часов; если её создали на десктопе, на телефоне появится
уведомление «Открыть». Как это работает и что учесть:

- Запросы браузера телефона идут телефон → реле → ваш Mac → `localhost:ПОРТ` и обратно. В отличие от чатов это
  **не** сквозное шифрование (реле должно читать страницы, чтобы их отдавать), поэтому превью доверяет реле.
- Страница отдаётся с **второго имени** того же сервера (по умолчанию `www.` + ваш домен, либо задайте
  `AGENT8S_PREVIEW_ORIGIN`). Это другой origin, чем у приложения, поэтому скрипты открытого сайта не доберутся до
  сохранённого ключа приложения. Сайты используют абсолютные ссылки (`/app.js`), поэтому превью занимает корень
  этого имени, а нужный сайт выбирается cookie `HttpOnly` (только для этого хоста), которую выдаёт ссылка-вход;
  без cookie посетителей этого имени перенаправляют на основной домен. Одно превью на браузер одновременно.
- **Сайты без мобильной вёрстки** (у некоторых админок на узком экране виден только боковое меню): отметьте у открытого
  превью «Показывать как на компьютере» и обновите страницу на телефоне. Страница построится в ширину компьютера
  (её тег `viewport` заменяется), и её можно приближать. В списке HTML-файлов только файлы самого чата: папки других
  проектов и чатов не показываются.
- Не поддерживается: WebSocket (горячая перезагрузка dev-сервера не обновит страницу сама), потоковые ответы
  (SSE), ответы больше 5 МБ. Редиректы на `localhost:ПОРТ` и cookie с `Domain=` переписываются, чтобы входы
  в аккаунт продолжали работать.
- Второе имя должно указывать на тот же nginx и входить в его сертификат; конфиг `server` для него приведён в
  английской версии выше (раздел про превью; контейнер реле `agent8s-relay`, cookie `a8p`).


## 5д. Телефон

Телефон показывает те же чаты и проекты, что и десктоп, и управляет теми же агентами. Это PWA (тот же
интерфейс в мобильной вёрстке): ничего собирать и подписывать не нужно — откройте ссылку в Safari и
добавьте на экран «Домой».

```
iPhone (Safari / приложение на «Домой») --WSS--> реле на вашем сервере <--WSS-- Mac (agent8s-desktop)
          \______________ сквозное шифрование, реле только пересылает байты ______________/
```

Обе стороны подключаются к реле **исходящими** HTTPS-соединениями (порт 443): работает за домашним NAT и в
мобильных сетях, где SSH закрыт; дома используется тот же путь, отдельного режима по локальной сети нет.

**Настройка реле** (один раз). Это один небольшой контейнер за уже работающим nginx:

1. Выложить: `PROXY_NETWORK=<docker-сеть вашего nginx> relay/deploy.sh <ssh-хост>` (собирает интерфейс,
   копирует его вместе с `server.py`, запускает `docker compose up`; порт на хосте не публикуется).
2. Пробросить путь в этом nginx — конфиг тот же, что в английской версии выше (раздел Phone).

**Подключение телефона:** задайте `AGENT8S_RELAY_URL=https://ваш.домен/agent8s` в `.env`, откройте десктоп,
«Телефон» → «Создать QR-код», наведите камеру iPhone и откройте ссылку в Safari. Чтобы поставить как
приложение: на открывшейся странице «Скопировать ключ», затем «Поделиться» → «На экран „Домой“», откройте
приложение и нажмите «Вставить ключ» (iOS хранит данные приложений с экрана «Домой» отдельно от Safari, поэтому
ключ передаётся один раз). Пока подключение включено, приложение не даёт Mac уснуть (`caffeinate`);
десктоп должен быть запущен (достаточно `agent8s-desktop --no-window`).

**Модель безопасности.** Ключ сопряжения — 32 случайных байта, их видно только в QR-коде. Из него обе стороны
выводят идентификатор комнаты и ключ AES-256-GCM (HKDF-SHA256); реле не знает ни того, ни другого. В
аутентифицируемые данные кадра входят направление и комната, каждый запрос несёт одноразовое число, выданное
Mac именно этому соединению, и строго растущий счётчик (перехваченные кадры нельзя проиграть заново, даже
после перезапуска), а Mac пропускает только фиксированный список эндпоинтов `/api/...`. Скомпрометированное
реле может задерживать или терять трафик, но не может его читать или подделывать. Идентификатор комнаты
передаётся в первом сообщении WebSocket, а не в URL, поэтому его нет в логах доступа. В браузере ключ хранится
как неизвлекаемый `CryptoKey` в IndexedDB. Оговорка: если реле живёт на одном origin с другими сайтами домена
(путь, а не поддомен), скрипт, внедрённый на *их* страницу, смог бы воспользоваться ключом; отдельный поддомен
это исключает. «Новый QR-код» меняет ключ и отключает все телефоны; «Отключить» удаляет его. Кто видел QR-код,
может запускать агентов на вашем Mac — храните его как SSH-ключ.

Пока нет: прямого режима по локальной сети, push-уведомлений (iOS ограничивает их для веб-приложений с экрана
«Домой»). Чтобы сторона Mac стартовала сама при входе в систему, см. «Фоновый запуск» выше.

## 5б. Вопрос без задачи: /ask

```
/ask как устроена авторизация в этом проекте?
/ask найди все места, где вызывается YandexGPT API
```

`/ask <текст>` запускает агента прямо в реальной папке проекта — без
worktree, без ветки, без задачи в базе — в режиме строго «только чтение»
(`--permission-mode plan` у claude, `-s read-only` у codex). Проверил
вживую: оба честно отказываются что-либо писать (claude объясняет, что не
может выйти из plan-режима, чтобы применить правку; у codex сама песочница
отклоняет запись) — поэтому это безопасно гонять прямо на настоящей рабочей
копии, а не только на worktree. Если нужно реально что-то поменять — это
обычная задача (свободный текст), не `/ask`.

## 5в. Отложенные и прерванные задачи: /continue

Два случая, когда задача не активна, но и не потеряна:

- **Прервана.** Если процесс бота умирает посреди задачи (краш,
  force-kill) — задача не может это пережить, при следующем запуске она
  помечается `interrupted` (не `failed`), если успела дойти хотя бы до
  одного хода и у неё есть `session_id`: claude/codex сами хранят сессию на
  диске независимо от нашего процесса. `failed` — значит сессии нет, и
  продолжать нечего.
- **Отложена.** `/diagnose` (ниже) временно откладывает текущую активную
  задачу в сторону, чтобы занять слот чата под самофикс, не теряя, чем ты
  занимался.

`/continue` восстанавливает то, что применимо: отложенную задачу чата, если
такая есть, иначе — последнюю тронутую задачу чата в статусе
`active`/`interrupted`. Возвращает её в обычный слот и показывает текущий
diff — следующее сообщение продолжит её как любое обычное уточнение.

## 6. Jira / Confluence

Работает только с Jira/Confluence **Server или Data Center** (не Cloud), через
Personal Access Token. Создать токен: аватар (справа сверху) → Profile →
Personal Access Tokens → Create token.

В `.env`:

```
JIRA_URL=https://jira.твоя-компания.ru
JIRA_PERSONAL_TOKEN=...
CONFLUENCE_URL=https://confluence.твоя-компания.ru
CONFLUENCE_PERSONAL_TOKEN=...
```

Оба блока независимы — можно заполнить только Jira. Если оставить пустыми,
`/context` и `/task` просто ответят, что Atlassian не настроен.

```
/context PROJ-123
```
— вытащить заголовок, статус, описание тикета и связанные страницы
Confluence (через remote links в самом тикете) и показать текстом. Никаких
вызовов агента и worktree — просто «покажи мне, что там в тикете».

```
/task PROJ-123 ещё добавь юнит-тест на этот кейс
```
— то же самое, но дальше запускает обычный конвейер задачи (worktree →
агент → diff → approve/drop), используя тикет как контекст, а твою фразу —
как техзадание. Нужен выбранный проект (`/use`) и отсутствие уже активной
задачи в чате.

Контекст тянется напрямую по REST из оркестратора (детерминированно, без
LLM), а не через MCP-инструменты, которыми агент рылся бы сам — так дешевле
и `/context` показывает ровно то, что увидит агент, ещё до старта задачи.

## 7. Яндекс.Календарь

Нужен **пароль приложения**, а не обычный пароль аккаунта:
id.yandex.ru → Безопасность → Пароли приложений → создать новый.

CalDAV-адрес календаря: в веб-версии Календаря → Настройки календаря →
вкладка «Экспорт».

```
YANDEX_CALDAV_URL=https://caldav.yandex.ru/calendars/твоя_почта%40yandex.ru/events-XXXXXXXX/
YANDEX_CALDAV_LOGIN=твоя_почта@yandex.ru
YANDEX_CALDAV_PASSWORD=пароль_приложения
```

**Важно для корпоративного Яндекс 360:** пароль приложения может
активироваться не сразу (у нас на практике — пара часов), а на некоторых
доменах администратору сначала нужно включить доступ по IMAP/CalDAV для
аккаунта — без этого будет `401` даже с правильным паролем. Проверить,
заработало ли, можно без запуска всего бота:

```bash
uv run scripts/check_caldav.py
```

Дальше:

```
/today       — список сегодняшних событий (время, название, место)
```

Напоминания работают фоновым циклом прямо внутри процесса бота (не отдельный
cron — проще, когда бот и так запускается вручную): раз в
`AGENT8S_REMINDER_POLL_SECONDS` (по умолчанию 300 сек) проверяет события,
которые начнутся в ближайшие `AGENT8S_REMINDER_LEAD_MINUTES` (по умолчанию 15
мин), и присылает сообщение всем чатам из `ALLOWED_CHAT_IDS`. Каждое событие
помечается в SQLite как «уже напомнили», чтобы не дублировать при повторных
проверках. Никакого LLM в этой цепочке нет — только чтение календаря и
отправка сообщения.

Если оставить переменные CalDAV пустыми — `/today` скажет, что не настроено,
а цикл напоминаний просто не запустится.

## 7а. Yandex Cloud: баланс

```
/balance
```

Прежде чем делать, проверил документацию — настоящих вебхуков для биллинга
в Yandex Cloud нет (каналы уведомлений Monitoring — email/SMS/push/
Telegram/Cloud Functions, а не произвольный URL; у ресурса `Budget` свои
уведомления уходят только на аккаунты пользователей Yandex Cloud, не на
внешние адреса), и живого REST-API для детализации расходов по сервисам за
день тоже нет — только через CSV-экспорт в Object Storage, который
настраивается один раз в консоли. Раз в первый заход эту настройку решили
не делать — сейчас только баланс: тот же паттерн опроса, что у напоминаний
календаря, а расход оценивается по разнице баланса во времени, а не по
реальной детализации по сервисам.

Billing API требует настоящий IAM-токен, а не статический API-ключ
(проверил — Billing нет в списке сервисов, принимающих API-ключи
напрямую), а личный OAuth-токен сама документация не рекомендует для
автоматизации — так что нужен **сервисный аккаунт** с **авторизованным
ключом** (JWT, подписанный PS256, обменивается на IAM-токен на ~12 часов,
обновляется автоматически):

1. Консоль → облако, к которому привязан твой биллинг-аккаунт → Сервисные
   аккаунты → Создать → выдать роль `billing.accounts.viewer` на
   биллинг-аккаунт.
2. Этот сервисный аккаунт → Создать новый ключ → Создать авторизованный
   ключ → скачать JSON-файл, положить в `./data/` (в `.gitignore`) —
   соответствует `YC_SERVICE_ACCOUNT_KEY_FILE`.
3. ID биллинг-аккаунта — в URL консоли / в разделе «Биллинг».

```
YC_SERVICE_ACCOUNT_KEY_FILE=./data/yc-authorized-key.json
YC_BILLING_ACCOUNT_ID=
YC_BALANCE_ALERT_THRESHOLD=
```

Механику сборки и обмена JWT проверил вживую против настоящего
`iam.api.cloud.yandex.net` (с одноразовой тестовой парой ключей — обмен
корректно упал на «неизвестный аккаунт», как и должен был) — сама
механика верна, для реального баланса нужен настоящий ключ сервисного
аккаунта.

- `/balance` — текущий баланс плюс расход/пополнение за последние ~сутки
  (ближайший снимок баланса к отметке «24 часа назад» против текущего —
  это оценка, не бухгалтерия, так как API по операциям нет).
- Фоновый цикл опрашивает раз в `YC_BALANCE_POLL_SECONDS` (по умолчанию
  1800 сек), сохраняет снимок и шлёт сообщение всем чатам из
  `ALLOWED_CHAT_IDS`, как только баланс упадёт ниже
  `YC_BALANCE_ALERT_THRESHOLD` — не чаще раза в
  `YC_BALANCE_ALERT_COOLDOWN_HOURS` (по умолчанию 12), чтобы не спамить,
  пока баланс низкий.

Если оставить `YC_SERVICE_ACCOUNT_KEY_FILE`/`YC_BILLING_ACCOUNT_ID`
пустыми — `/balance` скажет, что не настроено, а цикл сразу выключится при
старте.

## 9. Бот чинит и дорабатывает сам себя: /diagnose, /improve, /restart, /autostart

```
/diagnose бот завис на 17 часов без единого сообщения, задача #3 была в статусе running вечно
/improve добавь команду /whoami, которая показывает chat_id этого чата
/restart
/autostart on
```

`/diagnose [симптом]` и `/improve <что добавить/изменить>` — обе команды
направляют бота на его собственный исходный код, через один и тот же
механизм (`_run_self_task`), но с разной рамкой промпта: `/diagnose` —
«разберись в причине бага, вот хвост лога», `/improve` — «реализуй фичу в
стиле существующего кода». Какую вызывать — зависит от того, чинишь баг или
добавляешь возможность. Обе при первом вызове регистрируют бота как проект
(имя `agent8s`, путь вычисляется из `__file__`, ничего настраивать не нужно)
и запускают обычную задачу по нему — worktree, ветка, живой прогресс,
`/diff`, `/approve` — тот же конвейер, что и для любой другой задачи.
`/diagnose` дополнительно подмешивает в промпт хвост `data/bot.log` (файл с
ротацией, переживает рестарт — не просто stdout, который исчезает вместе с
терминалом); `/improve` — просит агента свериться с `handlers.py`/`agents/`
как образцом стиля и обновить README, если добавляется что-то, достойное
документации. Обеим явно сказано не мержить и не перезапускать самому. Если
в чате была активная задача по другому проекту — она откладывается (см.
`/continue` выше), а не блокируется и не теряется — работать над ботом можно,
не бросая то, чем занимался.

`/approve` для самофикса/доработки только мержит ветку — работающий процесс
всё ещё выполняет старый код из памяти (Python не умеет hot-reload).
`/restart`
перезапускает процесс на месте (`os.execv`, тот же PID, блокировка от
повторного запуска сохраняется), чтобы смерженное изменение реально
применилось; это отдельный, явный шаг специально — ты решаешь, когда, а не
момент мержа решает за тебя.

`/autostart on|off|status` оборачивает macOS LaunchAgent
(`~/Library/LaunchAgents/com.agent8s.bot.plist`, `RunAtLoad` + `KeepAlive`),
чтобы бот переживал логин и краши без открытого терминала — CLI-эквиваленты:
`scripts/install_launchagent.sh` / `scripts/uninstall_launchagent.sh`.
**Известная нерешённая проблема**: как минимум на одной машине процесс,
запущенный именно через launchd, зависает намертво на самом старте
интерпретатора Python (застревает на чтении `.venv/pyvenv.cfg` — подтвердил
через `sample` на зависшем PID) — тот же самый бинарник, запущенный точно
так же, но не через launchd, стартует меньше чем за секунду. Похоже на
macOS TCC/песочницу, блокирующую доступ к файлам под `~/Documents` для
LaunchAgent без интерактивного согласия пользователя, но не подтверждено;
чинится это, скорее всего, вручную через Системные настройки → Конфиденциальность
и безопасность — так, как я не могу сделать без диалогового окна. Пока
причина не найдена, считай `/autostart` установленным, но не проверенным
рабочим, и пользуйся `./scripts/run.sh` вручную; на `/restart` это не влияет
— он перезапускает уже работающий, уже получивший все разрешения процесс, а
не создаёт новый через launchd.

## 10. Безопасность

Эта машина выполняет shell-команды (через тот CLI, что ты выберешь) над
твоими локальными репозиториями по команде из Telegram. Помимо белого списка
`ALLOWED_CHAT_IDS`:

- `AGENT8S_CLAUDE_ALLOWED_TOOLS` / `AGENT8S_CLAUDE_PERMISSION_MODE` и
  `AGENT8S_CODEX_SANDBOX` в `.env` ограничивают, что агент может делать без
  человека в цепочке — в headless-режиме спросить разрешения не у кого.
- `/approve` никогда не пушит и не деплоит — только локальный merge. Пуш
  остаётся ручным отдельным шагом.
- Регистрируй (`/add_project`) только те репозитории, в которых тебе
  спокойно от того, что там будет работать LLM.
- Все секреты (токен бота, PAT для Jira/Confluence, пароль CalDAV) живут
  только в `.env`, который в `.gitignore` — в публичный репозиторий не
  попадают.
- Worktree — это откуда берётся git diff задачи, а не файловая песочница:
  `Bash`/`Edit`/`Write` спокойно пойдут по абсолютному пути куда угодно, если
  попросить в промпте (например «заодно поправь и библиотеки, от которых это
  зависит»). Иногда это ровно то, что нужно — но такие правки лягут прямо в
  твою настоящую рабочую копию, минуя `/diff`/`/approve`/`/drop` целиком.
  Держи это в голове, формулируя задачу.

## 11. Надёжность

21.08.2026 задача зависла в статусе «running» на 17+ часов без единого
сообщения — разобрался и поправил две реальные проблемы:

- **Блокировка от повторного запуска.** Ничто не мешало запустить второй
  `agent8s-bot` поверх первого — и так и случилось, накопилось четыре
  процесса за несколько дней перезапусков в новых терминалах без остановки
  старых, все на одном Telegram-токене. Теперь при старте берётся
  эксклюзивный flock на `<data dir>/bot.lock` — второй процесс сразу
  откажется стартовать с понятным сообщением, а не будет молча соревноваться
  за апдейты.
- **Восстановление при старте.** Статус задачи менялся с `running` только
  когда её собственная корутина-обработчик успешно завершалась — но если она
  падает без предупреждения (крах, force-kill, необработанное исключение
  посреди работы), задача так и остаётся `running` навсегда, а чат — вечно
  заблокирован на ней, без единого сообщения об ошибке. `running`-задача не
  может пережить процесс, который её запустил, так что теперь при каждом
  старте все оставшиеся `running`-задачи переводятся в `interrupted` (можно
  продолжить через `/continue` — см. выше) или `failed` (сессия так и не
  пришла, продолжать нечего), активная задача чата сбрасывается, а в сам чат
  уходит объяснение, что произошло.
- Отправка live-прогресса в Telegram (`ProgressReporter`) теперь ловит
  `TelegramAPIError` целиком, а не только `TelegramBadRequest` — шквал
  правок сообщения от частых вызовов инструментов мог упереться в лимит
  Telegram на редактирование и вызвать `TelegramRetryAfter`, которое раньше
  просто убивало корутину задачи. А сам вызов `agent.start()`/`.resume()`
  теперь обёрнут так, что любое неожиданное исключение превращается в
  обычный неуспешный результат, а не в необработанный краш — смысл именно в
  том, чтобы задача больше не могла тихо умереть без всякого следа.
- Оба ридера подпроцессов агентов теперь передают `limit=16 * 1024 * 1024` в
  `asyncio.create_subprocess_exec` (`STREAM_LIMIT` в `claude_agent.py` /
  `codex_agent.py`). Поймал вживую через ту же защиту от исключений выше:
  задача `/improve`, читающая свой же (большой) `handlers.py`, породила
  строку stream-json длиннее лимита `StreamReader` в 64 КБ по умолчанию —
  `LimitOverrunError`. Молча превратилось в неуспешный результат вместо
  зависшей задачи, но саму причину стоило починить, а не оставлять чтение
  любого крупного файла подброшенной монеткой.
